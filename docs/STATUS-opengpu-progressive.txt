Progressive decode through OpenGPU (2026-11-05, skeptic pass)
=============================================================

Supersedes the DWT_INV-only hook (d8ee7cd) and the I420 YUV pilot
(ogpu_yuv.c, never bit-exact).

What moved into OpenGPU (gfopenrtg stream v1.10, gfopengpu.library 0.27)
- RLGR1 entropy decode + LL3 delta sum           OGPU_OP_RLGR_DEC  0x002A
- dequantize + inverse 5/3 DWT (Y, Cb, Cr)       OGPU_OP_RFX_TILE  0x002B
- YCbCr -> ARGB32 (16.16, [MS-RDPRFX] 3.1.8.2.5) OGPU_OP_RFX_YCBCR 0x002C
- (DWT_INV 0x0029 stays for callers that only want the transform)

What stays in GFAmigaRDP (src/codec/progressive.c)
- WBT block / region / tile PDU parsing, quant tables, rectangles + view clip
- tile state (coef, sign, bitpos), sub-band diffing, first-pass merge
- SRL + raw upgrade passes (read/write per-coefficient sign state)
- trim / paint after pan

Hooks: struct rdp_prog_accel { rlgr, tile } (progressive.h), installed by
src/amiga/ogpu_prog.c from session_win.c. Per tile: one Submit of 3 x
RLGR_DEC (first/simple passes), one Submit of RFX_TILE + one RFX_YCBCR per
clipped rectangle (32 per batch; more go in follow-on batches). All
rectangles clipped away: skip RFX_TILE / YCBCR (no paint work).

ONGPU gate (skeptic claim 1)
- rdp_ogpu_prog_install only arms hooks when OGPU_Query answers with
  OGPU_ONGPU set for RLGR_DEC / RFX_TILE + RFX_YCBCR.
- The library's CPU core answers OGPU_FULL without OGPU_ONGPU_BIT, so a bare
  68040 keeps progressive.c's own CPU kernels (same maths, no Submit
  overhead). A real GPU driver (ACRTG.gpu / PiStorm.gpu) that claims ONGPU
  takes the Submit path.
- Also prevents a quiet host path if an ACRTG runtime is rebuilt with 0.27
  and "answers as the core does" (FULL, no ONGPU).

CPU fallback (after ONGPU install)
- gfopengpu.library missing, or Query NONE / no ONGPU: accel not installed.
- A Submit/Wait error other than OGPU_ERR_DATA: that hook returns 0 and the
  step is redone on the CPU in-tree (stats.cpu_fallback counts it).
- OGPU_ERR_DATA from RLGR_DEC = RDP_PROG_E_PROTO, as the CPU decoder says.

Bit-exactness / tests
- gfopenrtg tests/test_rfx.c: ops vs progressive.c kernels (copied), random.
- tools/test_prog_ogpu.sh (GFOPENRTG=checkout): whole synthetic frames
  (simple / first / upgrade, both DWT layouts, clip + paint) decoded with
  and without the accel: pixel-exact, stats equal (40 seeds).
- Same host binary also covers (skeptic claim 1 leftovers):
  * OGPU_ERR_DATA -> RDP_PROG_E_PROTO (no cpu_fallback on that step)
  * failed follow-on batch (>32 rects) -> cpu_fallback, whole tile on CPU
  * tiles with more than 32 rectangles (batching, pixel-exact)
  * all rects clipped away: tile hook returns 1 with zero Submits
- Stand-in SRC slots are 16 KB; copies are clamped (no 65535-into-16KB overrun).
- The stand-in mirrors ogpu_prog.c's batching / ERR_DATA / nrects==0 control
  flow; Amiga address maths (px + y * w + x, OGPU_XY) still need Cradle
  exercise (stove build below).

Behaviour change (small): first_pass decodes all three components before
touching the tile, so a malformed component no longer leaves the tile
half-merged. Decode scratch grows by 2 x 8 KB (vals x 3) + 8 B per rect.

Naming: the OpenGPU hook is rlgr1 (three-component RLGR1). OGPU_RLGR_MODE3
(RLGR3) remains UNSUPPORTED in the library.

Not yet
- ACRTG / PiStorm ONGPU for these ops (no driver claim yet).
- No live Windows / GNOME RD pixel capture through the new path yet.
- No 68040 timings of Submit-vs-in-tree (gated off until ONGPU).
